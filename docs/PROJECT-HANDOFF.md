# Передача проекта PFinance

Дата комплекта: 25 июля 2026 года.

## 1. Источник истины

Текущая рабочая версия находится в:

- `index.html` — деплой;
- `finance-dashboard.html` — идентичная копия.

Эти два файла должны оставаться одинаковыми. При расхождении главным считается `index.html`.

Исходные ТЗ в этой папке являются исторической основой. Они не полностью описывают поздние функции, поэтому нельзя откатывать код к первоначальным шести типам операций или к RUB/window.storage.

## 2. Текущая архитектура

- Один HTML-файл: HTML + CSS + чистый JavaScript.
- Внешние зависимости:
  - Google Fonts;
  - `@supabase/supabase-js@2` через ESM (`esm.sh`).
- Хранение: одна JSONB-строка состояния `S` на пользователя в `public.app_state`.
- Supabase: last-write-wins через `upsert` всей структуры `S`.
- RLS: пользователь читает и изменяет только строку со своим `user_id`.
- Нет `localStorage` и `sessionStorage`.
- В памяти используется `window.__mem` как временная страховка при сетевой ошибке.

Публичный anon-ключ уже встроен в HTML. Никаких `service_role`-ключей или паролей в проект добавлять нельзя.

## 4. Авторизация

Пользователь вводит имя и пароль. Имя преобразуется в технический email:

`username` → `username@pfinance.flexico.by`

Используется `signInWithPassword`. Формы регистрации в приложении нет. Пользователи создаются вручную в Supabase Authentication → Users с `Auto confirm user`.

В Supabase публичная регистрация должна быть отключена. Пароль существующего пользователя в архив не включён.

Текущая настройка клиента: `persistSession:false`. Это соблюдает запрет на browser storage, но после перезагрузки страницы может потребоваться повторный вход.

## 5. Текущая валюта и курсы

- Базовая валюта: BYN.
- Символ: `Br`.
- Начальное состояние содержит рабочую структуру ИП/ООО, пять точек и четыре банковских счёта с нулевыми остатками. Демо-операций, долгов и целей нет.
- Стандартные валюты: BYN, USD, EUR, RUB.
- Курсы при запуске загружаются из официального API НБРБ:
  `https://api.nbrb.by/exrates/rates?periodicity=0`
- Курс одной единицы рассчитывается как `Cur_OfficialRate / Cur_Scale`.
- При недоступности API используются последние сохранённые курсы.
- Все денежные значения отображаются с двумя знаками после запятой.

## 6. Актуальные функции поверх исходного ТЗ

### Счета

- Счёт бывает личным либо принадлежит конкретному ИП/ООО.
- Для счёта бизнеса сохраняются банк и список доступных точек того же юрлица.
- Один счёт можно связать с несколькими точками; его банковский остаток показывается только один раз.
- Валюта, владелец и стартовый баланс редактируются только до первой связанной операции.
- «Сверить баланс» создаёт `account_adjustment`, а не меняет историю задним числом.
- Счёт без истории можно удалить; счёт с историей архивируется.

### Бизнес

- Добавлены редактируемые юридические лица ИП/ООО.
- Каждая точка обязательно относится к юридическому лицу.
- Доход/расход бизнеса сохраняет точку и реальный связанный банковский счёт.
- Карточка точки показывает собственную аналитику, а реальный остаток счёта — раздел «Счета» и уровень юрлица.
- «Сверить аналитику» создаёт `biz_adjustment` и не меняет банковский счёт.
- Точку с историей удалить нельзя.

### Переводы

Добавлен тип `transfer`:

- `fromAccount` — счёт списания;
- `toAccount` — счёт зачисления;
- `amount` — сумма списания в валюте исходного счёта;
- `toAmount` — зафиксированная сумма зачисления в валюте целевого счёта.

Перевод не является доходом или расходом. Обычный `transfer` разрешён только между личными счетами либо между счетами одного юридического лица. Для движения между ИП и ООО используется `entity_transfer` с назначением операции. При разных валютах конвертация фиксируется в момент операции по текущим курсам.

### Корректировки

- `account_adjustment`: поля `account`, `delta`.
- `biz_adjustment`: поля `biz`, `delta`.

Корректировки меняют баланс, но не входят в доходы/расходы и не должны искажать месячную аналитику.

## 7. Важные расширения модели

Счёт дополнительно может иметь:

```js
{ archived: boolean }
```

Дополнительные операции:

```js
{
  type: "transfer",
  fromAccount,
  toAccount,
  amount,
  toAmount,
  date,
  cat,
  note
}

{
  type: "account_adjustment",
  account,
  delta,
  date,
  cat,
  note
}

{
  type: "biz_adjustment",
  biz,
  delta,
  date,
  cat,
  note
}
```

Нельзя удалять поддержку этих полей при дальнейших изменениях.

## 8. Что нельзя ломать

- Разделение личных денег и денег бизнеса.
- `draw` и `contribution` не являются личным доходом/расходом.
- Переводы и корректировки не являются доходом/расходом.
- Мультивалютность и фиксацию суммы перевода.
- Долги с частичными возвратами.
- Прогноз и цели.
- Мобильную нижнюю навигацию, шторки, таблицы-карточки и safe-area.
- Supabase RLS и хранение единого JSON-объекта.
- Экспорт/импорт JSON.
- Формат денег с двумя знаками после запятой.

## 9. Известные ограничения и замечания

1. Из-за `persistSession:false` сессия не переживает полную перезагрузку страницы.
2. При параллельном редактировании на двух устройствах действует last-write-wins.
3. В боковой панели может оставаться историческая подпись о локальном хранении, хотя фактически данные сохраняются в Supabase. Это косметическая неточность, которую можно исправить отдельной правкой.
4. Исходное ТЗ говорит о шести типах операций; актуальный код также содержит `transfer`, `account_adjustment` и `biz_adjustment`.

## 10. Проверка после любой доработки

- Вход по `admin`/другому username работает через технический email.
- Создание и изменение счёта сохраняются после повторного входа.
- Перевод уменьшает один счёт и увеличивает другой, не меняя доходы/расходы.
- Удаление перевода возвращает оба баланса.
- Корректировка меняет баланс и не попадает в доход/расход.
- Архивный счёт отсутствует в форме новой операции, но виден в истории и итогах.
- Название бизнес-точки редактируется.
- Все суммы показываются в формате `1 234,56 Br`.
- Курсы НБРБ обновляются без разрушения приложения при сетевой ошибке.
- Данные другого Supabase-пользователя недоступны благодаря RLS.
- На телефоне нижняя навигация и модальные шторки работают как раньше.

## 11. Модель версии 4.0.0

Состояние дополнено массивом:

```js
legalEntities: [
  { id, name, type: "ip" | "ooo", archived }
]
```

Точка бизнеса:

```js
{ id, name, emoji, legalEntityId, opening, archived, technical? }
```

Счёт:

```js
{
  id, name, bankName, emoji, kind, currency, opening, limit, archived,
  scope: "personal" | "business",
  legalEntityId: string | null,
  businessIds: string[]
}
```

Доход и расход бизнеса теперь содержат одновременно `biz` и `account`. Счёт обязан принадлежать тому же юрлицу и быть связанным с выбранной точкой.

Вывод/взнос содержат:

```js
{
  type: "draw" | "contribution",
  biz,
  account,          // личный счёт
  businessAccount,  // расчётный счёт бизнеса
  amount,           // сумма по личному счёту
  businessAmount    // зафиксированная сумма по бизнес-счёту
}
```

`ensureBusinessModel()` запускается после загрузки Supabase и после импорта JSON. Он сохраняет старые данные, добавляет недостающие поля и создаёт только отсутствующие элементы рабочей структуры.

### Проверка версии 4.0.0

- В разделе «Бизнес» видны ИП, ООО и пять фактических точек.
- Счёт ООО · Альфа-Банк отображается один раз и связан с двумя студиями ООО.
- При выборе Студии Куйбышева или Машерова форма предлагает один и тот же счёт ООО.
- При выборе Студии Толбухина форма предлагает счёт ИП · Альфа-Банк.
- Доход бизнеса увеличивает одновременно счёт и аналитику точки.
- Расход бизнеса уменьшает одновременно счёт и аналитику точки.
- Обычный перевод ИП → ООО блокируется; для него доступна отдельная операция «Между ИП и ООО».
- Личные итоги не включают счета ИП и ООО.

## 12. Модель версии 4.1.0: безналичные и общая касса

В `legalEntities` добавлена системная запись:

```js
{ id: "le-cash", name: "Наличные", type: "cash", system: true }
```

Она является интерфейсной группой общей кассы, а не реальным юридическим лицом. Точки по-прежнему принадлежат ИП или ООО.

Точка получила поля:

```js
{
  cashOpening: number,
  acceptsCash: boolean
}
```

Три студии имеют `acceptsCash: true`. Кофейня, Вендинг и служебное направление ООО используют только безналичный канал.

Общая касса хранится как системный бизнес-счёт:

```js
{
  id: "acc-studios-cash",
  name: "Наличные · 3 студии",
  kind: "cash",
  scope: "business",
  legalEntityId: "le-cash",
  sharedCash: true,
  system: true,
  businessIds: [
    "biz-tolbukhina",
    "biz-kuibysheva",
    "biz-masherova"
  ]
}
```

Для доходов, расходов, выводов и взносов бизнеса сохраняется:

```js
paymentMethod: "bank" | "cash"
```

- `bank` требует банковский счёт того же юрлица, что и точка;
- `cash` требует общую кассу и доступен только точкам с `acceptsCash: true`.

Добавлен тип операции:

```js
{
  type: "cash_transfer",
  biz,
  fromAccount,
  toAccount,
  amount,
  toAmount,
  cat: "Инкассация"
}
```

В операции должен участвовать ровно один общий кассовый счёт и один банковский счёт выбранной студии. Такая операция перемещает остаток между каналами точки и не влияет на выручку, расходы или прибыль.

`ensureBusinessModel()` обновляет `meta.modelVersion` до `5`, создаёт кассу и переносит прежние `business.opening` студий в `cashOpening`. Старые бизнес-операции с банковским счётом считаются безналичными; операции без счёта у студий считаются наличными.

### Проверка версии 4.1.0

- В разделе «Бизнес» рядом с ИП и ООО отображается карточка «Наличные».
- У каждой студии отображаются отдельные строки «Безналичные» и «Наличные».
- Наличная выручка любой из трёх студий увеличивает общую кассу.
- Безналичная выручка Толбухина идёт на счёт ИП · Альфа-Банк.
- Безналичная выручка Куйбышева и Машерова идёт на общий счёт ООО · Альфа-Банк.
- Инкассация выбранной студии уменьшает её наличные и увеличивает её безналичный остаток на ту же сумму.
- Прибыль при инкассации не изменяется.

## 13. Модель версии 4.2.0: мультивалютные долги и личная оплата бизнеса

### Долги

Долг хранится в собственной валюте:

```js
{
  id,
  dir: "in" | "out",
  who,
  amount,
  currency,
  date,
  due,
  note,
  repaid: [
    { amount, date, txId }
  ]
}
```

`amount` и элементы `repaid` всегда выражены в `debt.currency`.

При создании или возврате долга может появиться связанное движение по личному счёту:

```js
{
  type:
    | "debt_issue"
    | "debt_borrow"
    | "debt_repayment_in"
    | "debt_repayment_out",
  account,
  amount,       // фактическая сумма в валюте счёта
  debtId,
  debtAmount,   // сумма обязательства в валюте долга
  date,
  cat,
  note
}
```

Эти операции меняют только баланс личного счёта. Они не включаются в личные доходы, расходы и средний денежный поток.

Общие суммы долгов считаются через `toBase(remaining, debt.currency)`. Карточки долгов и платежи отображаются в исходной валюте обязательства.

### Личная оплата за бизнес

Один платёж хранится одной операцией с массивом распределения:

```js
{
  type: "personal_biz_expense",
  account,      // личная карта / счёт
  amount,       // общая сумма в валюте личного счёта
  allocations: [
    { biz, amount }
  ],
  settlement: "reimburse" | "contribution",
  cat,
  date,
  note,
  debtIds
}
```

Сумма всех `allocations.amount` должна совпадать с `amount` с точностью до 0,01.

Операция:

- уменьшает личный счёт один раз на `amount`;
- добавляет каждой точке бизнес-расход в размере её доли;
- не меняет кассу и банковские счета бизнеса;
- при `settlement: "reimburse"` создаёт по одному долгу каждого задействованного юрлица перед владельцем.

Автоматический долг имеет:

```js
{
  kind: "owner_reimbursement",
  legalEntityId,
  sourceTxId,
  currency: personalAccount.currency
}
```

Возмещение проводится существующей операцией `draw` с категорией `Возмещение личных расходов`. Такая операция меняет бизнес-счёт и личный счёт, но исключается из `monthAgg().draw` и `bizStats().draw`. После движения пользователь отдельно отмечает погашение автоматического долга.

`ensureBusinessModel()` обновляет `meta.modelVersion` до `6`, добавляет старым долгам отсутствующую валюту и не требует изменений таблицы `app_state`.

### Проверка версии 4.2.0

- Долг в USD может быть выдан с BYN-счёта с отдельной фактической суммой списания.
- Получение займа увеличивает личный счёт и не считается доходом.
- Возврат или погашение долга меняет счёт и не считается доходом/расходом.
- Платёж личной картой распределяется между тремя студиями и уменьшает их прибыль.
- При равном распределении между одной студией ИП и двумя студиями ООО создаются два долга: одна доля ИП и две доли ООО.
- Удаление долга удаляет связанные движения по личным счетам.
- Удаление операции «Личная оплата за бизнес» удаляет созданные ею требования к возмещению.
